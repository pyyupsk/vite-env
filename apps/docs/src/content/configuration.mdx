## Plugin options

```ts
import ViteEnv from '@vite-env/core/plugin'

ViteEnv({
  configFile: string                // required — no default
  allowedServerEnvironments?: string[] // default: auto-detected
  onClientAccessOfServerModule?:    // default: 'error'
    'warn' | 'error' | 'stub'
})
```

`configFile` is the path to the env definition file, relative to the project root. It is required since 0.8.0. If you omit it, the plugin throws.

`allowedServerEnvironments` lists the Vite environment names that can import `virtual:env/server`. If you leave it empty (the default), the plugin uses `environment.config.consumer`. Vite 8 and later set this to `'server'` for known runtimes: Node, Deno, Bun, and edge runtimes such as `'workerd'`. If you give a list, the plugin matches environments by name instead. Add an edge runtime here if auto-detection gets it wrong.

This option was called `serverEnvironments` before 0.8.0. The old name still works, but it logs a deprecation warning. Version 1.0.0 will remove it.

The plugin detects server environments in this order:

1. `environment.config.consumer` (Vite 8+ built-in: `'server'` for known runtimes)
2. `ssr.config.experimental.environments` (custom runtime configs)
3. Default: `['ssr']`

`onClientAccessOfServerModule` sets what happens when a disallowed environment imports the server module. See [Guard modes](/docs/guard-modes).

## defineEnv()

Accepts `server`, `client`, an optional `presets` array, and an optional `clientPrefix`. Returns the merged schema.

```ts
import { defineEnv } from "@vite-env/core";
import { z } from "zod";

export default defineEnv({
  server: {
    DATABASE_URL: z.string().url(),
    SECRET_KEY: z.string().min(32),
    PORT: z.coerce.number().default(3000),
  },
  client: {
    VITE_API_URL: z.string().url(),
    VITE_APP_TITLE: z.string().default("My App"),
  },
});
```

By default, client keys must start with `VITE_`. If a client key does not, the plugin throws at startup. To use a different prefix, set `clientPrefix`.

### clientPrefix

Sets the prefix that client keys must start with. It takes one prefix or an array of prefixes.

```ts
import { defineEnv } from "@vite-env/core";
import { z } from "zod";

export default defineEnv({
  clientPrefix: "APP_", // client keys must start with APP_
  server: {
    DATABASE_URL: z.string().url(),
  },
  client: {
    APP_API_URL: z.string().url(),
    APP_TITLE: z.string().default("My App"),
  },
});
```

With more than one prefix:

```ts
export default defineEnv({
  clientPrefix: ["NEXT_PUBLIC_", "PUBLIC_"],
  client: {
    NEXT_PUBLIC_API_URL: z.string().url(),
    PUBLIC_SITE_NAME: z.string(),
  },
});
```

If you set `clientPrefix`, it wins over Vite's `envPrefix`. If you do not set it, the plugin checks for `VITE_` after Vite resolves its config, so Vite's `envPrefix` applies first.

## Server / client split

| Block    | Keys                                     | Available in              |
| -------- | ---------------------------------------- | ------------------------- |
| `server` | Any name                                 | `virtual:env/server` only |
| `client` | Must start with prefix (default `VITE_`) | Both modules              |

## Presets

Presets add platform variables to the schema. Pass them in the `presets` array:

```ts
import { defineEnv } from "@vite-env/core";
import { vercel } from "@vite-env/core/presets";
import { z } from "zod";

export default defineEnv({
  presets: [vercel],
  server: {
    DATABASE_URL: z.string().url(),
  },
});
```

If one of your keys has the same name as a preset key, your key wins. If two presets define the same key, the plugin logs a warning and the last preset wins. The output does not keep the `presets` key. It holds only the merged `server` and `client` shapes.

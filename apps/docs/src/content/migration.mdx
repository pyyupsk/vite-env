vite-env 0.8.0 is the last release before 1.0.0. It holds the breaking changes that fix the public API for 1.0. All changes are in one PR: [#87](https://github.com/pyyupsk/vite-env/pull/87), commit `06d7ca9`.

Run the codemod first. It does the renames and adds the missing `configFile` for you:

```bash
npx jscodeshift -t https://raw.githubusercontent.com/pyyupsk/vite-env/main/packages/core/scripts/codemod-0.8.mjs src/ vite.config.ts --dry --print
```

When the printed diff looks right, run the command again without `--dry --print` to write the changes.

---

## 1. `onClientAccessOfServerModule` default: `'warn'` → `'error'`

**What changed:** If you do not set `onClientAccessOfServerModule` and a disallowed environment (for example client code) imports `virtual:env/server`, the build now fails. Before, it printed a warning and exited with code 1.

**Why:** `'warn'` let teams add the guard step by step during 0.x. A server-only import in client code is a real bug, and a warning in CI logs is easy to miss. So the build now stops.

**Before/after:**

```ts
// Before (0.7.x) — implicit default was 'warn'
ViteEnv({ configFile: "./env.ts" });

// After (0.8.0) — implicit default is now 'error'
ViteEnv({ configFile: "./env.ts" });
// same call, different behavior. To keep the old behavior, set it explicitly:
ViteEnv({ configFile: "./env.ts", onClientAccessOfServerModule: "warn" });
```

**Codemod:** Not automated, because this is a change in behavior, not a rename.

**Manual steps:** If the new default breaks your build, fix the import. If you need time, add `onClientAccessOfServerModule: 'warn'` (or `'stub'` for shared test files) for now, and remove it when the build is clean.

## 2. `serverEnvironments` → `allowedServerEnvironments`

**What changed:** The option has a new name. In 0.8.x the old name still works, but it logs a deprecation warning. Version 1.0.0 removes it.

**Why:** The old name read like "the environments that are servers". The option means "the environments that can import the server module", and the new name says that.

**Before/after:**

```ts
// Before (0.7.x)
ViteEnv({ configFile: "./env.ts", serverEnvironments: ["ssr", "workerd"] });

// After (0.8.0)
ViteEnv({ configFile: "./env.ts", allowedServerEnvironments: ["ssr", "workerd"] });
```

**Codemod:** Automated. It renames `serverEnvironments` to `allowedServerEnvironments`.

## 3. `configFile` is now required

**What changed:** `ViteEnv()` used `./env.ts` when you did not set `configFile`. Now it throws in `configResolved` if `configFile` is missing.

**Why:** When the file was in a different place, the hidden default caused "my config is not used" bugs. With the path in `vite.config.ts`, you can see which file the plugin reads.

**Before/after:**

```ts
// Before (0.7.x): no arguments, used './env.ts'
ViteEnv();

// After (0.8.0): throws "[vite-env] configFile is required..."
ViteEnv();

// Fix: always pass it explicitly
ViteEnv({ configFile: "./env.ts" });
```

**Codemod:** Automated. It adds `configFile: './env.ts'` to every `ViteEnv()` call that does not have it, with or without an options object.

## 4. `defineEnv()` no longer forwards arbitrary keys

**What changed:** `defineEnv({ ... })` used to copy any key other than `server`, `client`, `presets`, and `clientPrefix` into its result. Now it throws on an unknown key.

**Why:** Nobody planned this behavior. A typo such as `severs: {...}` for `server: {...}` passed without an error, and the return type could not be exact.

**Before/after:**

```ts
// Before (0.7.x): extra keys copied without a warning
export default defineEnv({
  server: { DATABASE_URL: z.string().url() },
  extraMetadata: { team: "platform" }, // silently kept on the result
});

// After (0.8.0): throws
// "[vite-env] Unknown keys in defineEnv(): extraMetadata.
//  Only "server", "client", "presets", and "clientPrefix" are allowed."
```

**Codemod:** Not automated. The codemod finds the call and prints a warning:

```
[codemod] src/env.ts:8: defineEnv has custom keys [extraMetadata] that are no longer allowed. Move them to a separate config or use presets.
```

**Manual steps:** Move the extra keys out of `defineEnv()`. Put them in a separate exported object or config module. If several `defineEnv()` calls share them, make a custom `EnvPreset`.

## 5. `ValidationResult.errors` type change

**What changed:** `ValidationResult['errors']` and `StandardValidationResult['errors']` used to be `z.core.$ZodIssue[]` for Zod and `StandardValidationIssue[]` for Standard Schema. Both are now one type, `ValidationError[]`:

```ts
type ValidationError = {
  message: string;
  path: readonly (string | number)[];
  code?: string;
};
```

**Why:** Before, code that called `validateEnv()` or `validateStandardEnv()` needed to know which library made the result to read `.path`. Zod issues hold raw `PropertyKey` values. Standard Schema issues hold `PathSegment` objects with a `.key`. Now both give a plain `(string | number)[]`, so one piece of error code works for both.

**Before/after:**

```ts
// Before (0.7.x)
const result = validateEnv(def, rawEnv);
if (!result.success) {
  for (const issue of result.errors) {
    // issue.path: (string | number | symbol)[], the Zod shape
    console.log(issue.path.join("."), issue.message);
  }
}

// After (0.8.0): same code, but path is always (string | number)[]
const result = validateEnv(def, rawEnv);
if (!result.success) {
  for (const error of result.errors) {
    console.log(error.path.join("."), error.message, error.code);
  }
}
```

`formatStandardSchemaError` is removed. Both libraries now give `ValidationError[]`, so `formatZodError` formats both:

```ts
// Before (0.7.x)
import { formatStandardSchemaError, formatZodError } from "@vite-env/core/format";

// After (0.8.0): one function for both
import { formatZodError } from "@vite-env/core/format";
```

**Codemod:** Not automated, because only types changed. After you upgrade, run `tsc --noEmit`. Code that reads Zod-only `$ZodIssue` fields, such as `.input` or `.expected`, shows a type error.

## 6. `zod` peer dependency is now optional

**What changed:** `@vite-env/core`'s `zod` peer dependency is now `peerDependenciesMeta: { zod: { optional: true } }`.

**Why:** Projects that use only `defineStandardEnv()` (with Valibot, ArkType, or another Standard Schema library) never needed Zod, but npm and pnpm still warned about the missing peer dependency. The plugin now loads `zod` only when you call `defineEnv()`.

**Before/after:**

```bash
# Before (0.7.x): always both
npm install @vite-env/core zod

# After (0.8.0): Standard Schema users install only their validator
npm install @vite-env/core valibot
```

If you use `defineEnv()`, nothing changes. Keep `zod` installed.

**Codemod:** Not needed. This change affects only what you install.

## Rollback notes

If 0.8.0 breaks your build and you need more time:

1. Pin back to `0.7.x` in `package.json` (`"@vite-env/core": "^0.7.0"`) and reinstall.
2. To stay on 0.8.0 with the old guard behavior, set `onClientAccessOfServerModule: 'warn'`. This is the only change in 0.8.0 that you can switch back with an option.
3. In 0.8.x, `allowedServerEnvironments` and `serverEnvironments` both work. The old name only logs a warning, so you do not need to change it back.
4. The unknown-key error in `defineEnv()` and the `ValidationResult.errors` type change have no option to turn them off. To undo them, pin 0.7.x.

## FAQ

**"configFile is required" error after upgrading, but I never set it before.**
Your config used the old `./env.ts` default. Add `configFile: './env.ts'` (or the path to your file) to `ViteEnv({...})`.

**My build started failing after upgrading, no code changes on my end.**
The cause is almost always the new `onClientAccessOfServerModule` default. Code in your client bundle imports `virtual:env/server`. Fix the import. If you need time, set `onClientAccessOfServerModule: 'warn'` until you find it. The build output names the environment that did the import.

**Deprecation warning: "serverEnvironments is deprecated. Use allowedServerEnvironments instead."**
In 0.8.x both names work the same. Run the codemod or rename the option yourself. In 1.0.0, the old name will throw.

**`defineEnv()` throws "Unknown keys in defineEnv()" for a key that used to work fine.**
Your config used the removed key forwarding. Move that key out of `defineEnv()`. The plugin never validated or typed it.

**TypeScript errors on `result.errors[i].path` after upgrading. It used to accept `symbol` in the path array.**
`ValidationError.path` is now `(string | number)[]`. Code that expects Zod's raw `PropertyKey[]`, which can hold a `symbol`, needs an update. This affects only schemas with symbol keys, which are rare.

**Do I need to run the codemod, or can I do this by hand?**
For one or two config files, follow the sections above by hand. For a monorepo with many `vite.config.ts` and `env.ts` files, run the codemod. It does items 2 and 3, which are most of the work in a typical project.

**Where did `StandardValidationIssue` go?**
It is now part of `ValidationError`. See [item 5](#5-validationresulterrors-type-change). If you import `StandardValidationIssue` as a type, replace it with `ValidationError`.
